# ADR 交叉引用（Cross-Reference）

> 本文档记录 `docs/adr/` 下全部 11 份 ADR 之间的交叉引用关系、隐性依赖、层级细化关系和已知交叉风险。
>
> 维护规则：新增 ADR 时同步更新本文档。更新日期：2026-07-08。

---

## 图例

| 关系类型 | 标识 | 含义 |
| --- | --- | --- |
| **细化** | ⤵ 细化 | ADR-B 是对 ADR-A 中某个决策的进一步细化/正式化 |
| **构建** | ⤴ 构建于 | ADR-B 的决策建立在 ADR-A 的决策之上 |
| **依赖** | ➡ 依赖 | ADR-B 的实现依赖 ADR-A 的决策先落地 |
| **引用** | 🔗 引用 | ADR-A 在文本中引用了 ADR-B 的决策 |
| **同层** | ↔ 同层 | 两个 ADR 属于同一架构层次，无直接依赖关系 |
| **交叉风险** | ⚠️ 风险 | 两个 ADR 的决策之间存在潜在冲突或边界未定义 |
| **无关** | — 无关 | 两个 ADR 的决策范围不相交 |

## 交叉风险

| # | 涉及 ADR | 类型 | 描述 | 可能性 | 影响 | 缓解建议 |
| --- | --- | --- | --- | --- | --- | --- |
| CR-01 | ADR-008 ↔ ADR-009 | **演进冲突风险** | V3 引入 JWT 时，如果认证端点响应格式/鉴权方式发生 breaking change（如匿名 token → JWT 的 payload 结构不同），将触发 ADR-009 的新 API 版本（`/api/v2/`）。当前两 ADR 均未定义此边界 | 低 | 中（需额外 API 版本协调） | V3 设计时评估认证端点是否需要走 `/api/v2/` 而非在 v1 升级。V2 保持匿名 token 在 v1 增加端点即可。**✅ 已记录到 ADR 正文**：ADR-008 §后果 + ADR-009 §负面/限制 |
| CR-02 | ADR-001 ↔ ADR-006 | **依赖完整性** | ADR-006 要求区分「规则 vs LLM」样本用于权重校准，但 `logs` 表的 schema 是否包含 `llm_enabled` 字段未在 DB DDL 中明确 | 低 | 低（V2 实现时补充即可） | V2 校准实现时确认 logs.output 包含 llm_enabled 标记 |

## 维护规范

1. **新增 ADR 时**：同步更新本文档的矩阵、细化表、依赖表、阶段链。
2. **修改 ADR 状态**：更新关联 ADR 的引用关系（如 Superseded 需更新细化/依赖关系）。
3. **交叉风险消除**：修复后更新风险状态 `CR-xx: ✅ 已关闭`，并标注关闭日期与关联 ADR/PR。
4. **一致性检查**：每次 ADR 审查时运行本文档的对比，确认无遗漏交叉引用。
