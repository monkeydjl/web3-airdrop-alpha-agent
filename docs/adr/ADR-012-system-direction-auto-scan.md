# ADR-012: 系统方向反转为自动扫描全网发现平台

- **Status**: Accepted
- **Date**: 2026-07-09
- **Deciders**: 产品 / 架构 / 后端
- **技术栈**: 多源采集、采集调度器、SQLite→PostgreSQL
- **影响面**: 数据源、数据库 schema、调度、API、安全、成本、运维

---

## 背景

Web3 Airdrop Alpha Agent System 在 v1.x 阶段定位为"用户手动输入项目 → 系统分析评分"的工具。该模式在设计与早期验证中暴露两个硬约束：

1. **慢**：依赖用户人工发现项目，覆盖速度远落后于市场节奏。Web3 空投机会窗口通常为数天到数周，人工发现的项目进入分析时往往已错过最佳参与期。
2. **不全面**：用户信息网络有盲区，无法系统性覆盖 DefiLlama 3000+ 协议、Twitter VC/KOL 信号、链上新合约部署等多维度来源，大量早期机会被遗漏。

方向不反转的后果：系统价值停留在"单次分析工具"，无法承担"早期项目发现平台"的产品定位，用户需自行承担发现成本，与系统价值主张冲突。

方向反转的约束条件：
- **兼容性**：不破坏既有 API（`/run` 手动输入保留）、不丢失历史数据（已评分项目保留）
- **成本可控**：采集源 API 费用需在 $100-500/月预算内
- **可渐进**：MVP 阶段仅接入免费源即可验证方向，付费源按需接入
- **安全合规**：自动采集引入 Prompt Injection 风险，需对齐 `SECURITY.md §10`

---

## 决策

**系统方向从"手动输入评分工具"反转为"自动扫描全网的发现与评分平台"。**

### 1. 定位反转

| 维度 | v1.x（旧） | v2.0（新） |
|------|-----------|-----------|
| 定位 | 手动输入驱动的评分工具 | 自动扫描全网的发现与评分平台 |
| 项目发现 | 用户负责 | 系统主动采集 |
| 数据源 | 手动录入 + V2 被动补全 | 多源自动采集 + 手动补充 |
| 调度 | 仅分析调度 | 双调度：采集调度 + 分析调度 |
| 用户角色 | 项目发现者 + 分析请求者 | 评分消费者 + 反馈提供者 |

### 2. 核心决策项

| 决策项 | 选择 | 理由 |
|--------|------|------|
| **发现方式** | 多源自动采集（DefiLlama/GitHub/CoinGecko/Twitter/链上/任务平台） | 覆盖度优先，免费源即可启动 |
| **手动输入** | 保留，降级为补充能力 | 覆盖采集盲区，不破坏既有 API |
| **调度模型** | 双调度器（采集 + 分析） | 采集与分析解耦，频率独立 |
| **采集表** | 新增 4 张表（data_sources/raw_projects/project_signals/collection_logs） | 采集数据量大，需独立 processed 状态管理 |
| **评分体系** | 保留 6 维评分 + FARM/WATCH/IGNORE | 分析能力不变，只变发现方式 |
| **LLM 预算** | **分级使用**（见下文"LLM 预算决策"） | 自动扫描量大，原 $1/日 预算不足 |

### 3. LLM 预算决策（关键子决策）

自动扫描模式下，预期每日分析 20-50 个项目。原 `.env.example` 中 `LLM_DAILY_BUDGET_USD=1.0`（$1/日）按单项目 $0.05 计算需 $2.5/日，超预算 2.5 倍。

| 方案 | 描述 | 被否理由 |
|------|------|----------|
| 方案 A：提高预算至 $3-5/日 | 所有项目都走 LLM 增强 | 成本不可控；且低质量项目不值得消耗 LLM |
| 方案 B：完全关闭 LLM | 仅规则引擎 | 失去 LLM 对高价值项目的深度分析价值 |
| **✅ 当前决策：分级使用 LLM** | 仅 `discovery_score ≥ 0.7` 的高价值项目启用 LLM，其余走规则引擎 | 兼顾成本与分析质量 |

**分级规则**：
- `discovery_score ≥ 0.7` → 启用 LLM 增强（预期 5-10 项目/日，$0.25-0.50/日）
- `0.3 ≤ discovery_score < 0.7` → 仅规则引擎
- `discovery_score < 0.3` → 不进入分析管道（仅存信号）

**配置变更**：
- `LLM_DAILY_BUDGET_USD` 保持 $1.0（分级后足够）
- 新增 `LLM_DISCOVERY_SCORE_THRESHOLD=0.7`（控制 LLM 启用门槛）

### 4. 数据迁移决策

- `projects` 表已有项目：保留，补 `auto_discovered=false`、`discovery_source='manual'`
- `scores`/`logs` 表：保留（历史评分是 golden 回归基线）
- `scripts/seed.py` 策展数据：保留（演示与测试基线）
- 新增 4 张采集表 + projects 扩展 4 个字段（带 DEFAULT，不破坏已有记录）

## 理由

| 备选方案 | 被否理由 |
|----------|----------|
| **方案 A：保持 v1.x 纯手动输入** | 覆盖慢、盲区大，用户已明确否决 |
| **方案 B：混合模式（手动为主 + 辅助推荐）** | 推荐仍依赖初始手动输入，未解决"发现覆盖度"核心问题；推荐算法需大量历史数据冷启动 |
| **方案 C：纯自动扫描（完全移除手动输入）** | 过激：采集源有盲区（未上 DefiLlama 的新项目、未公开代码库的项目），用户无法补充；破坏既有 API 兼容 |
| **✅ 当前决策：自动扫描为主 + 手动输入为补充** | 兼顾覆盖度（自动扫描）+ 兜底（手动补充）；不破坏既有 API；可渐进式接入数据源 |

### 选中理由（客观）

1. **覆盖度可验证**：自动扫描每日发现 20-50 候选项目，远超人工发现的 1-3 个/日
2. **成本可控**：免费源（DefiLlama/GitHub/CoinGecko）即可覆盖 60%+ 发现需求；LLM 分级使用后预算不超
3. **兼容性**：保留手动输入路径，既有 API 不破坏，历史数据可复用
4. **可渐进**：分 5 阶段实施，MVP 阶段仅接入免费源即可验证方向
5. **可回退**：KPI 未达预期时可回退 v1.x 混合模式（保留手动输入路径是回退前提）

---

## 后果

### 正面

- **覆盖度提升**：从人工 1-3 项目/日提升至系统 20-50 候选/日
- **时效性提升**：新项目发现→评分延迟 < 1 小时（v1.x 依赖用户触发）
- **用户价值转移**：用户从"发现者"转为"决策者"，聚焦评分消费与反馈
- **数据资产积累**：`raw_projects`/`project_signals` 形成早期项目信号库，长期可用于模型训练

### 负面 / 限制

- **成本增加**：采集源 API 费用 $100-500/月（v1.x $0-100/月）
- **复杂度增加**：新增采集调度器、速率限制器、4 张采集表、降级矩阵
- **运维负担**：外部 API 故障需监控与降级处理（`OPERATIONS.md §4.3` 已补充采集故障 runbook）
- **安全风险**：外部数据进入 LLM 分析，需 Prompt Injection 防御（`SECURITY.md §10.1`）
- **存储增长**：年增约 450MB 采集数据（需归档策略）

- **代码迁移**：Collector 从被动转主动，需重写；其他 Agent 不变
- **API 迁移**：`/run` 保留，新增 `/discoveries`；无 breaking change
- **配置迁移**：`.env.example` 新增 8 个字段，均为可选（默认空）
