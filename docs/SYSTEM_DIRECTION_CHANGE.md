## 📋 执行摘要

本文档记录 Web3 Airdrop Alpha Agent System 的**产品方向反转决策**。

> **新定位（v2.0）**：系统是一个**自动扫描全网的 Web3 早期项目发现与评分平台**。
> 系统主动从多数据源（DefiLlama / Twitter / 链上 / GitHub / 任务平台等）持续发现未空投的早期项目，经多 Agent 分析后输出 FARM/WATCH/IGNORE 评分与建议。

**方向反转原因**：原 v1.x 定位为"用户手动输入项目 → 系统分析"，实践发现该模式存在两个硬约束：
1. **慢**：依赖用户人工发现项目，覆盖速度远落后于市场
2. **不全面**：用户信息网络有盲区，遗漏大量早期机会

新方向将项目发现从"人工驱动"转为"系统主动驱动"，用户角色从"项目发现者"转为"评分消费者/决策者"。

## 🔄 方向反转对比

| 维度 | v1.x（旧方向） | v2.0（新方向） |
|------|---------------|---------------|
| **定位** | 手动输入驱动的评分工具 | 自动扫描全网的发现与评分平台 |
| **项目发现** | 用户负责 | 系统主动采集 |
| **数据源** | 手动录入 + V2 被动补全 | 多源自动采集 + 手动补充 |
| **调度** | 仅分析调度（cron 触发已录入项目） | 双调度：采集调度（发现）+ 分析调度（评分） |
| **实时性** | 用户触发即跑 | 持续采集 + 定时/触发式分析 |
| **用户角色** | 项目发现者 + 分析请求者 | 评分消费者 + 反馈提供者 |
| **价值核心** | 分析质量 | 发现覆盖度 + 分析质量 |
| **成本** | $0-100/月（外部源可选） | $100-500/月（采集源必需） |

## 🎯 新产品定位（v2.0，确定）

### **定位: 自动扫描全网的 Web3 早期项目发现与评分平台**

```
用户角色: 评分消费者 + 反馈提供者（不再是项目发现者）
系统角色: 主动发现者 + 深度分析者
价值链:   系统的发现覆盖度 + 系统的分析准确度
```

**系统能力（v2.0 核心）**:

| 能力 | 说明 | 阶段 |
|------|------|------|
| **多源自动采集** | DefiLlama / Twitter / 链上 / GitHub / 任务平台持续扫描 | MVP/V1 |
| **新项目发现** | 从采集数据中识别"未发币 + 有活跃度"的早期项目 | MVP/V1 |
| **去重与归一化** | 多源命中同项目自动合并，跨 run 稳定 id | MVP/V1 |
| **多 Agent 分析** | Narrative/Team/Risk/Tokenomics + Scorer 六维评分 | 既有 |
| **三档分类** | FARM/WATCH/IGNORE + 可解释理由 | 既有 |
| **手动补充** | 用户可手动添加项目（补充采集盲区） | MVP/V1 |
| **反馈闭环** | 用户对结果标注 → 权重校准 | V2 |

## 🏗️ 新架构（v2.0）

```
┌─────────────────────────────────────────────────────────┐
│                   多数据源（自动采集）                    │
│  DefiLlama · Twitter/X · 链上 · GitHub · Galxe/Layer3   │
└──────────────────────────┬──────────────────────────────┘
                           │ 采集调度（独立 cron，持续运行）
                           ▼
┌─────────────────────────────────────────────────────────┐
│              采集管道（Collection Pipeline）              │
│  拉取 → 归一化 → 去重 → 新项目识别 → 写入 raw_projects   │
└──────────────────────────┬──────────────────────────────┘
                           │ 新项目入队 / 定时触发
                           ▼
┌─────────────────────────────────────────────────────────┐
│              分析管道（Analysis Pipeline，既有）          │
│  Collector → Narrative → Team → Risk → Tokenomics        │
│           → Scorer → Orchestrator                        │
└──────────────────────────┬──────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────┐
│              结果展示 + 用户反馈                          │
│  Dashboard（FARM/WATCH/IGNORE 列表）· Watchlist · 反馈   │
└─────────────────────────────────────────────────────────┘
                           ▲
                           │ 手动补充（用户可添加采集盲区项目）
┌──────────────────────────┴──────────────────────────────┐
│                   手动输入（补充，保留）                   │
│  UI 录入 · CSV 导入 · 单次 API · seed 演示                │
└─────────────────────────────────────────────────────────┘
```

### **双调度模型**

| 调度器 | 职责 | 频率 | 触发动作 |
|--------|------|------|----------|
| **采集调度器** | 发现新项目 | 按源不同：DefiLlama 每日 / Twitter 实时流 / 链上事件 webhook | 拉取 → 去重 → 写入 `raw_projects` |
| **分析调度器** | 评分新项目 | 新项目入队即触发 + 定时批量（每小时） | 从 `raw_projects` 取未分析项目 → 跑 Agent Pipeline |

> 与 v1.x 的关键差异：v1.x 只有分析调度器，且数据来自用户手动输入。v2.0 新增采集调度器，系统主动发现项目。

## 📊 价值定位（自动扫描模式）

| 维度 | 自动扫描模式 |
|------|-------------|
| **项目发现** | 系统负责（多源持续扫描） |
| **分析深度** | 系统负责（6 维评分 + 可解释理由） |
| **时间投入** | 用户零发现成本，仅消费评分结果 |
| **机会覆盖** | 全网覆盖（受限于数据源 API 覆盖度） |
| **质量保障** | golden 回归 + 权重校准 + 用户反馈闭环 + 采集质量过滤 |
| **成本** | $100-500/月（采集源 API 费用） |

**ROI 逻辑**: 系统每日自动发现 N 个候选项目，产出 FARM/WATCH/IGNORE 决策 + 可解释理由。用户价值来自**发现覆盖度 × 分析质量**，而非单次分析。

## � 成功指标（KPI）

### **核心 KPI（v2.0 验收标准）**

| 指标类别 | 指标名 | 目标值 | 度量方式 | 度量频率 |
|----------|--------|--------|----------|----------|
| **发现覆盖** | 每日新发现候选项目数 | 20-50/日 | `raw_projects` 当日新增条数 | 每日 |
| **发现覆盖** | 去重后进入分析数 | ≥ 20/日 | `raw_projects.processed=true` 当日数 | 每日 |
| **发现覆盖** | 多源命中率 | ≥ 30% | 被 ≥ 2 个源命中的项目占比 | 每周 |
| **分析质量** | FARM 档命中率 | ≥ 5%/周 | FARM 项目中事后确认空投的比例 | 每月（反馈闭环） |
| **分析质量** | 评分稳定性 | ≥ 95% | 同项目 7 日内重跑分差 < 10 分的占比 | 每周 |
| **时效性** | 发现 → 评分延迟 | < 1 小时 | `discovered_at` 到 `processed_at` 的中位数 | 每日 |
| **时效性** | 采集成功率 | ≥ 95% | `collection_logs.status='success'` 占比 | 每日 |
| **成本效率** | 单项目发现成本 | < $1 | 月采集成本 / 月发现项目数 | 每月 |
| **成本效率** | 单项目分析成本 | < $0.05 | 月 LLM 成本 / 月分析项目数 | 每月 |
| **去重质量** | 去重准确率 | ≥ 95% | 1 - 误合并率 - 漏合并率 | 每周 |

### **KPI 达成判定**

- **MVP/V1 达标线**：前 4 项核心 KPI（发现覆盖 + 分析质量）连续 7 日达标 → v2.0 方向验证成功
- **V1+ 达标线**：全部 10 项 KPI 连续 30 日达标 → 自动扫描模式可持续运行
- **未达标处理**：若 MVP/V1 阶段 KPI 未达预期，触发方向复盘，评估是否回退 v1.x 混合模式

## ⚠️ 风险与挑战

### **业务风险**
1. **采集噪音** — 自动扫描会引入大量低质量项目
   - 缓解: 采集质量过滤（硬规则初筛 + Agent 深度分析）
2. **API 成本** — Twitter/链上数据源付费
   - 缓解: 分级接入（免费源优先 + 付费源按需），成本监控告警
3. **发现延迟** — 实时性受限于采集频率
   - 缓解: 关键源（Twitter/链上）用实时流/webhook，非关键源定时

### **技术风险**
1. **数据质量** — 多源数据冲突
   - 缓解: 去重归一化（ROADMAP §6.2.1）+ 来源优先级仲裁
2. **采集稳定性** — 外部 API 限流/故障
   - 缓解: 速率限制器 + 降级策略 + 重试机制
3. **存储增长** — `raw_projects` / `project_signals` 数据量大
   - 缓解: 数据保留策略（DATABASE_DDL §6）+ 定期归档

### **安全风险（新增）**
- 自动采集引入 Prompt Injection 风险（外部数据进入 LLM 分析）
- 缓解: `SECURITY.md §10.1` Prompt Injection 防御（输入隔离 + 输出约束）

## ✅ 决策记录

**决策**: 系统方向从"手动输入评分工具"反转为"自动扫描全网的发现与评分平台"。
**记录于**: 2026-07-09
**版本**: v2.0（替代 v1.x 的手动输入定位）
**依据**: 用户明确指令"手动分析太慢也不全面，改为自动扫描全网未空投的项目"

### **备选方案对比**

| 备选方案 | 描述 | 被否理由 |
|----------|------|----------|
| **方案 A：保持 v1.x 纯手动输入** | 用户手动发现项目 → 系统分析 | 覆盖慢、盲区大，用户已明确否决 |
| **方案 B：混合模式（手动为主 + 辅助推荐）** | 用户输入为主，系统基于已录入项目做相似项目推荐 | 推荐仍依赖初始手动输入，未解决"发现覆盖度"核心问题；推荐算法需大量历史数据冷启动 |
| **方案 C：纯自动扫描（完全移除手动输入）** | 系统全自动采集发现，移除手动输入 API | 过激：采集源有盲区（如未上 DefiLlama 的新项目、未公开代码库的项目），用户无法补充；破坏既有 API 兼容 |
| **✅ 当前决策：自动扫描为主 + 手动输入为补充** | 系统主动采集发现，保留手动输入覆盖盲区 | 兼顾覆盖度（自动扫描）+ 兜底（手动补充）；不破坏既有 API；可渐进式接入数据源 |

### **选中理由（客观）**

1. **覆盖度可验证**：自动扫描每日发现 20-50 候选项目，远超人工发现的 1-3 个/日
2. **成本可控**：免费源（DefiLlama/GitHub/CoinGecko）即可覆盖 60%+ 发现需求，付费源按需接入
3. **兼容性**：保留手动输入路径，既有 API 不破坏，历史数据可复用
4. **可渐进**：分 5 阶段实施，MVP 阶段仅接入免费源即可验证方向

**影响**:
