# UTF-8 编码损坏：现状、成因与修复方案

> 本文档记录仓库内文档的编码损坏问题。写下来的原因：这是**不可逆的数据
> 损失**，且其中三个文件连 git 历史都救不回来；不留档，下一个人只会看到一堆
> 莫名的 `?` 而不知道发生过什么。

## 1. 现状（2026-08-21 实测）

损坏分**三型**，成因同源（写回文件时没用 UTF-8，或用 `errors='replace'`
解码后又写回），但可修复性差别很大。

### 一型：非法 UTF-8 —— 3 字节字符丢了第 3 字节

| 文件 | 损坏处数 | 有干净历史底本？ |
|---|---:|---|
| `docs/DATA_SOURCE_STRATEGY.md` | 498 | ❌ 全部历史版本均已损坏 |
| `docs/OPERATIONS.md` | 404 | ✅ 提交 `6823d18` |
| `docs/OBSERVABILITY.md` | 214 | ✅ 提交 `6823d18` |
| **小计** | **1116** | |

### 二型：整字被替换成 `?` —— **仍是合法 UTF-8**

| 文件 | 损坏处数 | 有干净历史底本？ |
|---|---:|---|
| `docs/API_SPEC.md` | 70 | ⚠️ `6823d18` 有干净版，但内容已大幅改写 |

**二型更糟**，原因见 §3.2。

### 三型：字面 U+FFFD 替换符

| 文件 | 损坏处数 | 丢了什么 | 有干净历史底本？ |
|---|---:|---|---|
| `docs/SYSTEM_DIRECTION_CHANGE.md` | 2 | 两个小节标题的 emoji | ❌ 最早版本就已损坏 |

三型是**唯一损失可忽略**的一型：丢的是 `## 📊 成功指标（KPI）`、
`## 🗺️ 实施路线图` 这类标题里的装饰性 emoji，不影响任何语义。
成因也不同 —— 是"用 `errors='replace'` 解码后又写回"，不是编码写错。

判据反而最干净：正常写作绝不会输入 U+FFFD，所以**无需上下文、零误报**，
连代码块都不用排除。

**它是怎么被发现的**：写完二型检测后我主动追问"还有没有第三种形态"，
换判据重扫全仓才找到。教训是 —— **检测判据的盲区就是损坏的藏身处**，
"查完了"这个判断本身要有依据，不能靠感觉。

全仓其余 479 个文本文件编码正常（`python scripts/check_encoding.py` 实测，
退出码 0，5 个已登记文件按预期列为待修复；`--strict` 时 5 个全部判失败）。

## 2. 损坏形态

### 2.1 一型

每个 3 字节 UTF-8 中文字符的**第 3 字节被替换成 `?`（0x3F）**，前 2 字节完好。
实测 403 处替换为 `?`、1 处为 `.`。

```
原文：恢复。   ->  E6 81 A2  E5 A4 8D  E3 80 82
损坏：恢复?    ->  E6 81 A2  E5 A4 8D  E3 80 3F
                                            ^^ 被吃掉的字节
```

文件因此变成非法 UTF-8 —— 至少还能被机械检测出来。

### 2.2 二型

**整个字符**被替换成一个半角 `?`：

```
原文：每个端点的请求/响应样例   ->  ... E8 AF B7 E6 B1 82 2F ...
损坏：每个端点的请?响应样例     ->  ... E8 AF B7 3F ...
                                              ^^ 「求/」两个字符一起没了
```

结果**完全合法**，`decode('utf-8')` 一点问题都没有 —— 一型的检查看不见它。

判据是"半角 `?` 紧贴中文字符"（中文语境里几乎不会这样用半角问号）。
**代码块与行内代码不判**：mermaid 流程图的判定节点是正常写法。实测加上这两条
排除后，3 个误报文件全部归零。有意思的是 `check_encoding.py` 自己
一度被自己误报 —— "描述判据的文字"和"符合判据的损坏"长得一样。

`?` 是编码转换失败的典型占位符 —— 说明某次写回时用了非 UTF-8 编码（很可能是
GBK 或系统默认 ANSI），无法表示的字符被替换。**这一步不可逆**：原字符信息
已从文件里消失。

git 历史显示一型出现在 `a9f2c8b` 之后潜伏 3 个提交，
二型同样起于 `a9f2c8b`，潜伏了 **6 个**提交。

## 3. 为什么不能"重写一遍就好"

### 3.1 一型：候选集有限，是"做选择题"

前 2 字节固定后，第 3 字节的合法取值只有 64 种，所以每处损坏是**从一个有限
候选集里挑一个字**，不是自由创作。实测各前缀的候选数量：

| 前缀 | 候选字符 | 全仓样本 | 主项占比 |
|---|---|---:|---:|
| `efbc` | 全角标点 6 种 | 16402 | 25.6% |
| `e294` | 框线 10 种 | 6339 | 77.9% |
| `e380` | 顿号句号书名号 6 种 | 6086 | 49.8% |
| `e286` | 箭头 5 种 | 1025 | 92.5% |

`efbc` 那一行是关键：四个全角标点各占 26/25/20/19%，**按频率猜的错误率接近
3/4**。把猜测直接写进文档，比留一个显眼的占位符更糟 —— 读者无法分辨哪句
是原文、哪句是机器编的，文档从此不可信。

### 3.2 二型：连候选集都没有，且不是 1 换 1

二型没有前 2 字节做约束，候选是**全部汉字**。更糟的是实测发现：
**一个 `?` 并不总是只吃掉一个字符**。逐行对齐底本后统计 24 处可核对的位置，
**恰好 1 个字符的：0 处；多于 1 个的：24 处**（例如 `求/`、`：\n`、`项 `）。

这意味着二型**连"1 字符换 1 字符"的结构约束都不成立** —— 没法像一型那样
用"下标恒定"的办法安全地逐位修复，也没法用逐字节校验证明修复没越界。

因此本项目的修复原则是：**只填能证明的，不填猜的**。二型目前**只做检测与
登记，不做自动修复**。

### 3.3 三型：可修，但没必要机械化

三型丢的是两个装饰性 emoji，而且 git 历史里最早的版本就已经坏了 ——
没有底本可对齐，同样无法证明原字符是哪个 emoji（从上下文只能推测
「成功指标」配 📊、「实施路线图」配 🗺️，那是猜的）。

区别在于**这两处的损失可以忽略**：不影响任何语义，只是标题少了个图标。
所以处理方式是**登记 + 检测防复发**，不写猜测值。
若哪天要修，直接手工补一个合适的 emoji 即可 —— 那属于内容编辑，不是数据恢复，
不应该由修复脚本代劳。

### 修复分四轮

1. **底本对齐**（432 处）：`OPERATIONS.md` / `OBSERVABILITY.md` 在 `6823d18`
   有干净版本，用 difflib 序列对齐**精确恢复**，不含猜测。
   注意两个实测踩到的坑：占位符本身对不上底本（要看左邻居反推）、
   损坏版是 CRLF 而底本是 LF（要先规范化，否则对齐全废）。
2. **语料唯一前缀**（27 处）：扫全仓未损坏文档统计每个前缀实际用过哪些字，
   若该前缀在整个项目里**只对应一个字**，填它是推断而非猜测。
3. **上下文规则**（170 处）：见下节。每条规则的准确率都在真实语料上量过，
   箭头规则已按实测收紧（曾是 187 处，收紧后少填 17 处 —— 刻意的退步）。
4. **人工选择题**（剩 487 处）：`--worklist` 导出 `docs/_utf8_worklist.json`，
   每条给出候选集与前后 40 字上下文；填好 `pick` 后用 `--choices` 合并，
   越出候选集的答案会被拒绝。

当前进度：**1116 处已定 629 处（56.4%）**，487 处待人工判定。

| 文件 | 损坏 | 已定 | 待定 |
|---|---:|---:|---:|
| `docs/OPERATIONS.md` | 404 | 303 | 101 |
| `docs/OBSERVABILITY.md` | 214 | 195 | 19 |
| `docs/DATA_SOURCE_STRATEGY.md` | 498 | 131 | 367 |

进度**比上一版低了**（原 646 处 / 58%）：箭头规则收紧后
`DATA_SOURCE_STRATEGY.md` 的 17 处箭头退回人工。这是刻意的 ——
详见下节的实测数据。

### 上下文规则怎么保证不写错字

每条规则先在干净文档上做**准确率实测**：把未损坏文档当 ground truth，
对每个符合规则条件的真实字符，检查规则会不会填对。

**重要提醒**：最初只用 `6823d18` 的 5 个文档量，四条规则都是 100%。
后来扩到全仓 **140 个既有文档**复测，发现样本一大就掉下来了：

| 规则 | 5 文档样本 | 140 文档样本 | 结论 |
|---|---|---|---|
| 括号 + 后紧跟表格竖线 | — | 518/518 = **100%** | 安全 |
| 括号 + 之后无括号 | 312/312 | 3469/3484 = 99.57% | 有反例 |
| 句末句号（行尾空白） | 210/210 | 2360/2375 = 99.37% | 有反例 |
| 箭头（前缀 e286 全填 `→`） | 72/72 | 912/989 = 92.21% | **已废弃，见下** |

也就是说**小样本给了虚假的安全感**。已知反例：
- 括号规则会把括号内部的逗号误填成右括号（`（**真实域名，含 localhost …）`）
- 句号规则会把右书名号 `」` 误填成句号（行尾正好收尾引号时）
- 箭头规则在缩进的架构图里会把 `↓` 误填成 `→`

不过对本次修复而言，这些规则的实际输出**已经过更硬的一道检验**：
在有底本的两个文件上，规则推断与底本对齐**独立**推断同一批位置，
结论必须完全一致 —— 实测 `OPERATIONS.md` 61 处、`OBSERVABILITY.md` 44 处可
核对，**冲突 0**。这条交叉验证固化在
`backend/tests/test_utf8_repair_tools.py` 里，规则一旦放松就会红。

#### 箭头规则已按实测收紧（2026-08-21）

无条件填 `→` 平均每 13 处写错 1 个字，这个错误率不能接受。
e286 前缀的真实分布（140 文档实测）：

| 字符 | 次数 | 占比 | 集中在 |
|---|---:|---:|---|
| `→` | 916 | 92.34% | 62 个文件 |
| `←` | 26 | 2.62% | `DELIVERY_CHECKLIST.md` 为主 |
| `↓` | 22 | 2.22% | `ENGINEERING_ROADMAP.md` 等 |
| `↔` | 15 | 1.51% | `ADR_CROSS_REFERENCE.md` |
| `↑` | 13 | 1.31% | `ENGINEERING_ROADMAP.md` |

关键观察：**全仓统计不可靠，但同一份文档内部的用法高度一致** ——
62 个含箭头的文档里 **56 个（90.3%）只用 `→`**。

所以判据从"全仓统计"改成"**本文档证据**"（`arrow_evidence()`）：
只有当这份文档（含其 git 底本）其余存活箭头**全都是 `→`** 时才允许填，
另加一条"整行只有箭头则弃权"（那是架构图的纵向连接符，`↓` 更常见）。

**留一法实测**（逐个隐藏一个箭头，只用同文档其余箭头判断，模拟真实处境
—— 我们看不见被损坏的那个字）：

| 判据 | 可填 | 正确率 | 弃权 |
|---|---:|---:|---:|
| 原规则（无条件填 `→`） | 992 | 92.34% | 0 |
| 仅"非缩进行" | 816 | 93.14% | 176 |
| 仅"左右均非空白" | 197 | 94.92% | 795 |
| **本文档证据** | 583 | 99.83% | 409 |
| **本文档证据 + 独行弃权** | 582 | **100%** | 410 |

注意前两种"看起来更聪明"的收紧（限缩语法位置）几乎没用 —— 涨到 93~95% 就停了。
**换判据的维度**（从"位置像不像"改成"这份文档怎么用箭头"）才有质变。

实际影响：`OPERATIONS.md`（底本 52 个 `→` 证据）与 `OBSERVABILITY.md`
（12 个证据）照旧可填；`DATA_SOURCE_STRATEGY.md` **无底本、存活箭头 0 个**，
17 处箭头**全部退回人工**。因此总待定数从 470 升到 **487** ——
**这是刻意的退步**：宁可多留 17 个显眼的占位符，也不写 1 个看似通顺的错字。

括号与句号两条留着，因为错误率在 0.5% 量级且被底本交叉验证兜住；
但它们**不是 100%**，见 §6，不当作"已证明"使用。

被量出来不合格因而**丢弃**的更宽松版本（留档，免得后人再试）：

- 「只要本行有未闭合 `（` 就填 `）`」→ 186/197 = **94.4%**。
  反例：`密钥轮换检查（V2+，超 90 天未换提醒）` —— 括号内部本身有逗号。
- 「前缀 e286 一律填 `→`」→ 912/989 = **92.21%**，已按上表换判据。

### 用法

```bash
python scripts/repair_utf8_docs.py                    # 报告，不写盘
python scripts/repair_utf8_docs.py --worklist         # 导出选择题清单
python scripts/repair_utf8_docs.py --apply            # 写 .partial（占位符标记待定处）
python scripts/repair_utf8_docs.py --choices docs/_utf8_worklist.json --apply
python scripts/verify_utf8_repair.py <损坏文件> <修复后文件>   # 校验修复合法
```

`--apply` 在仍有待定处时**只写 `.md.partial`，不动原文件** —— 半成品不入库。
校验器认得半成品里的待定占位符（`U+FFFD`），会把它与"填了个候选集外的字"
区分开：前者合法、后者判失败。

当前三个 `.partial` 全部通过校验：未损坏正文逐字节一致，已修复的字全部落在
候选集内。

## 5. 防复发

`.pre-commit-config.yaml` 的 `check-encoding` 钩子会拦下**三型**损坏，
任何新写入的编码损坏文件都进不了下一次提交。

已知损坏文件分三份清单登记在 `check_encoding.py` 里
（一型 `KNOWN_BROKEN`、二型 `KNOWN_BROKEN_MOJIBAKE`、
三型 `KNOWN_BROKEN_REPLACEMENT`），默认只警告不阻断
（否则这道检查一上线就把所有提交卡死）。
**修复完成后请从对应清单删除条目 —— 清单为空是目标状态**，
有测试专门断言"已修好的文件不该还留在清单里"。

另有两个测试把钩子的效果固化下来：
`test_no_unregistered_mojibake_in_repo` 与
`test_no_unregistered_replacement_char_in_repo` —— 全仓不得出现**未登记**的
二型 / 三型损坏。
